# 协作约定

> 这个项目现在有两个人（各自带着 AI 会话）在改。这份文档解决三件事：
> 代码在哪、每次开工收工做什么、哪些文件不许两个人同时动。
>
> 设计与进度看 `开发纪要.md`，要加东西查 `工程约定.md` 第五节的改动索引。
> 这份只管「怎么一起改」。

## 一、仓库

| 项 | 值 |
| --- | --- |
| 远端 | `git@github.com:Windows233/if-between.git`（私有仓库） |
| 主分支 | `main` |
| 认证 | SSH 密钥 |
| 体积 | 约 305 MB（`art/` 246 MB、`audio/` 31 MB、`docs/screenshots/` 33 MB） |

clone 要拉三百多兆，慢是正常的。**不要**为了「轻一点」把 `art/` `audio/`
挪出去，素材和代码分离会让两边都对不上。

### 被加为协作者才能推

私有仓库，光有 SSH 密钥不够。仓库所有者要在 GitHub 上：
`Settings → Collaborators → Add people`，把对方账号加进来。

加完之后，对方把自己机器的 SSH 公钥挂到自己 GitHub 账号上就通了。

## 二、第一次上手（只做一次）

```bash
git clone git@github.com:Windows233/if-between.git
cd if-between

# 1. 设自己的提交身份。仓库里带的是占位，不改的话分不清谁提交的
git config user.name  "你的名字"
git config user.email "你的邮箱"

# 2. 扫一遍，注册 class_name
GODOT="C:/Games/Steam/steamapps/common/Godot Engine/godot.windows.opt.tools.64.exe"
"$GODOT" --headless --path . --import

# 3. 确认现状没坏
"$GODOT" --headless --path . --script res://tests/run_tests.gd
python tools/check_data.py
```

第 2 步不能省。`class_name` 的注册表（`.godot/global_script_class_cache.cfg`）
不进版本控制，不跑 `--import` 就会出现一堆 `Identifier not declared`。

第 3 步期望：测试输出 `通过 1529 / 1529`，退出码 0；体检输出
`数据自查通过：8 张地图，9 份剧情，4 个结局`。

## 三、每次开工和收工

**开工第一件事：**

```bash
git pull
git status                            # 工作区干不干净
git log --oneline origin/main..main   # 本地有没有没推出去的东西
```

不 pull 就动手，等于闭着眼睛改。别人动过什么你完全不知道。

最后那条要养成习惯。**本地压着没推的提交，再叠一次 pull 或 merge，
很容易把同一批改动并成两份，历史就乱了。** 收工就 push，一半是为了防这个。

还有一条：跑 `git pull --rebase` 时留意它报的提交数。**数目对不上就是信号**，
说明本地有你不知道的提交，先停下来看清楚再往下走。

**收工前：**

```bash
"$GODOT" --headless --path . --script res://tests/run_tests.gd   # 必须退出码 0
python tools/check_data.py                                      # 必须退出码 0

git status                  # 看清自己动了什么，别把不该进的加进去
git add -A
git commit -m "说清改了什么"
git push
```

**测试不过不许 push。** 推上去的是别人接着要改的地基，坏的地基会连累对方排查半天。

## 四、分工（避免撞车）

按目录划所有权。**要动别人那一栏的文件，先说一声。**

| 线 | 目录 | 内容 |
| --- | --- | --- |
| 剧情内容线 | `data/events/`、`data/maps/` | 剧情节点、台词、IF 条件、地图定义 |
| 界面线 | `ui/`、`scenes/cutscene.gd` | IF 框、对话框、过场演出 |
| 引擎线 | `core/` | 条件判定、世界状态、数据解析 |
| 场景线 | `scenes/`（除 `cutscene.gd`） | 地图、角色、主入口 |
| 素材线 | `art/`、`audio/` | 图、音乐、音效 |
| 工具线 | `tools/`、`tests/` | 校验脚本、测试、探针 |

### 串行区（同一时间只能一个人动）

- **`core/` 里的公共类。** 加字段、改接口会让别人直接编译不过。要动先约时间。
- **`project.godot`、`export_presets.cfg`。** 这两个在 `.gitattributes` 里标了 `-merge`。
  自动合并错了是**静默坏掉**（autoload 丢了、导出预设被覆盖），不会报错。
- **`docs/开发纪要.md`。** 两边的 AI 会话都往里追加。

纪要的规矩很具体：**只追加，不改别人的小节。**
收工前先 `git pull`，再往文件末尾追加自己那节。这样冲突通常是「两块新增挨在一起」，
手工保留两边就完事。

## 五、错峰与同时改

**错峰**（不在同一时间段开工）最省事。前提只有一条：
开工先 pull，收工就 push，中间别拖太久。

**同时改**也能做，规矩多一点：

1. **谁都不许在 `main` 上长线开发。** 各开各的分支，从最新的 `main` 切出去。
2. **小步提交。** 每完成一个能跑通的小步骤就 commit 并 push 自己的分支。
   攒着不提交，冲突窗口就大，对方也不知道你做到哪了。
3. **动手前先 fetch**，看对方推了什么。
4. **合回 `main` 之前先 pull。** 顺序是 pull → merge → 跑测试 → push。

```bash
# 开工
git switch main && git pull
git switch -c feat/你的活

# 边做边提交，做完一步就推一次
git add -A && git commit -m "..."
git push -u origin HEAD

# 合回主线
git switch main
git pull
git merge feat/你的活
# 跑测试，两条都要过
git push
```

分支名用 `feat/`、`fix/`、`content/` 开头。两个人一起看的时候要分得清是谁的，
带上人名更好，比如 `win/if-panel`。

### 合回主线的两种做法

**做法一，在本地合。** 适合两个人、改动不大、彼此信得过。

```bash
git fetch origin
git log --oneline HEAD..origin/feat/xxx      # 先看对方改了什么
git diff --stat HEAD..origin/feat/xxx
git merge origin/feat/xxx
# 跑测试，两条都要过
git push
```

**做法二，走 Pull Request，在网页上审。** 想看 diff、想留讨论记录的时候用这个。

对方在 GitHub 上开 PR，base 选 `main`，compare 选自己的分支。你在 PR 页面能看清
改了哪些文件、每一行的差异，可以逐行留评论，也可以直接点 Merge。
合完把自己本地的 `main` 拉一下。

**「审核」要不要强制。**

GitHub 默认不拦人。协作者可以直接 `git push` 到 `main`，PR 只是个自觉流程。

要强制，得配分支保护规则。仓库 `Settings → Branches → Add branch protection rule`，
branch name pattern 填 `main`，勾上 `Require a pull request before merging`。
之后谁都不能直接推 `main`，一律走 PR。

注意，勾上之后**你自己**也推不了 `main`，连改一行文档都得走 PR。
两个人项目里这有点啰嗦，想清楚再开。

### 让两边的 AI 会话看得见对方

同时改最容易出的事故是：两个会话各自埋头改，谁也不知道对方在动什么，
等到合并时才发现撞了。

这个项目用两层机制解决。

**一层是 `.codebuddy/`，进版本控制，两边自动加载。**

- `.codebuddy/CODEBUDDY.md` —— 项目约定，会话启动时自动读
- `.codebuddy/settings.json` 的 `SessionStart` hook —— 会话一启动就跑
  `.codebuddy/hooks/session_status.sh`，把「远端有几个新提交、对方改了哪些文件、
  本地有没有未提交改动、`docs/进行中.md` 现在写着什么」**注入 Agent 的上下文**

所以两边的会话一开口就知道局面，不用谁去提醒。

注意 `settings.json` **不热加载**，改完要重开会话才生效。

**另一层是 `docs/进行中.md`，由人写。**

开工加一行，写清自己在哪条分支、正在改哪些文件、什么时候开始的。收工删掉。
Agent 读到这张表，发现要改的文件在别人行里，就会停下来问。

这套东西靠人遵守才有效。表格不填，hook 报得再准也是空的。

## 六、冲突怎么办

- **剧情 JSON**：两边改了同一段台词或同一个节点，**由人决定留哪个**。不要让 AI 顺手「解决」。
- **`project.godot` / `export_presets.cfg`**：一定人工处理，逐行看。
- **`docs/开发纪要.md`**：两边的小节都留。
- **`.godot/`**：不进版本控制，冲突不了。真乱了就删掉重跑 `--import`。

合完必须再跑一遍测试。没验过的合并不要推。

## 七、不要做的事

- 不提交 `.godot/`（`.gitignore` 已排除）。
- 不动工作区的换行符。`.gitattributes` 定了 `eol=lf`，仓库内一律 LF。
  没了这条，两人用不同编辑器时 diff 会整片失效，冲突根本没法解。
- 不直接改别人的分支。
- **提交身份要在自己机器上设成自己的。** 搭仓库时留的是 `Blodwyn / blodwyn@local`，
  那是占位，两个人提交混在一起就分不清是谁。只改这个仓库，不加 `--global`：

  ```bash
  git config user.name  "你的 GitHub 用户名"
  git config user.email "<用户 id>+<用户名>@users.noreply.github.com"
  ```

  邮箱用 noreply 格式，提交才会关联到自己账号（id 在 GitHub 设置页的 Emails 那一栏，
  或者 `https://api.github.com/users/<用户名>` 的 `id` 字段）。仓库现在设的是
  `Windows233 / 333727122+Windows233@users.noreply.github.com`。

  **改这个不用动历史提交。** 以前那些占位邮箱的记录留着就行 ——
  重写历史会让已经 clone 过的人 pull 出问题，得不偿失。
- 导出产物不进仓库。`*.pck`、`/build/`、`/export/` 已排除，
  正常落在 `../if-demo-build/`。

## 八、带 AI 会话时的注意事项

项目里配了 `.codebuddy/`：`CODEBUDDY.md`（项目约定）和 `SessionStart` hook
（启动时报告协作状态）。

### 自动注入看工作目录在哪

宿主的**项目级**配置是按**会话的工作目录**找的。工作目录就是项目目录时，
`CODEBUDDY.md` 会被自动读、hook 会被自动触发。工作目录落在别处时，两样都不生效，
而且**不会报错，只是一片安静**。

各家的会话工作目录不一定落在项目里。WorkBuddy 的桌面会话用的是它自己那套
`WorkBuddy/<时间戳>/` 目录，所以这类会话必须走下面这条手动入口。

### 开工第一条：跑一次状态脚本

```bash
bash <项目根>/.codebuddy/hooks/session_status.sh
```

脚本自己定位项目根，在哪个目录执行都一样。报四件事：当前分支、远端有没有新提交
（有的话连对方改了哪些文件一起列出来）、本地有没有未提交的改动、
`docs/进行中.md` 现在写着什么。

**这条不依赖自动注入，固定跑。** 报完再按第三节那三条走。

### 要交代的还有两件

- **收工前 commit 并 push。** 会话不会自己想起来，不写就留在工作区，
  下一轮谁手一滑就混进别人的提交。
- **开工先 pull。** 同样要明说，状态脚本只是提示，动作得它自己做。

### 另外三条

- `settings.json` 不热加载，改完要重开会话才生效。
- `--import` 和 Godot 编辑器不能同时跑，会抢 `.godot/`。
- 截图必须开真窗口（`--path` 不带 `--headless`），无头模式用 dummy 渲染器，截出来是空的。
