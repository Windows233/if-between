## 四 每次制定计划的工作步骤

1. 读取交接入口和状态账，查询当前分支/main/远端跟踪状态，注明核查版本。当前工作分支的“未跟踪”不等于main没有；不能把并行分支测试数拿来冒充主线数据。
2. 先收录用户新报告，再查工程。用稳定任务ID记录制作、交付、集成、验收四状态，附日期、用户原话或提交/文件证据。收到“已做未交”就安排提交验收；“日记已做漏包”就补收或按用户要求跳过。
3. 围绕下一段可玩链检查入口、状态写入、物品、分支、出口和资源引用。不只统计文件数量；对关键标志同时查读写。剧情正本、结局序号与内部ID分别对照。
4. 给5名制作成员排具体任务。用户只负责统筹，不安排其个人制作。每人最多120分钟，包含沟通、导出、自检和交接；不能把后备碰撞任务与出图再叠加两小时。
5. 每条写前置、工作、分钟、交付、验收、拿不到输入时的替代和超时降级。昨日未交项先核实：有稿返修，无稿首版；不能把昨天计划当实际完成。
6. 保留D1至D6制作、D7至D9润色。先砍额外CG和复杂系统表现，保住剧情因果、回溯快照、关键证据、操作反馈和章末交付。未到End7不能把End6失败结局当完整通关。
7. 生成同内容的Markdown/Word和结构化当日任务。核对总时长、前置依赖和重复派工，再按仓库规则验证、提交、推送；制定计划本身不运行游戏开发或自动把任务设为完成。

## 五 结构化字段与验证

`docs/项目进度.json`每个item包含`id/name/owner/production/delivery/integration/acceptance/evidence/next_action`。新状态覆盖旧结论时保留证据；只有收到交付并完成验证，才能将相关状态改为通过。未知写待确认，不编完成率。

每日`day_plan.json`包含`date/day/tasks`，每项有`id/owner/minutes/work/deliverable/acceptance/depends_on/fallback`。`depends_on`可以指进度ID或当天任务ID；存在依赖不表示该依赖已交。分支方案共用同一预算，不作为第二组任务累加。

在项目根运行：

```powershell
python tools/validate_daily_plan.py docs/每日策划/2026-10-24_D3/day_plan.json
```

校验器检查日期、任务编号、负责人、必要交付字段和每人120分钟上限。它不能证明剧情正确、功能已运行或素材已收到，这些仍需检查证据与实际版本。改技能后再运行skill-creator的`quick_validate.py`核对技能结构；保留隐式调用策略。
