# 剧情稿解读与制作规范 v1.0

2026年10月24日整理。适用于《剧情修改1.0版.docx》及后续同类剧情稿的阅读、拆分、实现和验收。

## 1. 文档目的

剧情稿同时包含玩家看到的内容、演出提示、分支结构、素材要求和作者备注。制作时必须先判断一段文字属于哪一种信息，再决定它进入对白、演出、地图、状态或待确认清单。

本规范解决四个问题：

- 识别剧情稿中的符号和固定写法。
- 把段落转换成当前工程使用的事件、节点、地图交互和状态。
- 区分已经实现、可以直接实现、缺少素材和仍需策划决定的内容。
- 保留原稿中的台词、顺序、分支意图和特殊断句，避免制作阶段自行补写剧情。

本规范是制作方法，不会把原稿自动视为已实现内容。剧情正本仍以 `docs/剧情/剧情修改1.0版.docx` 为准；当前实现状态以工程文件和 `docs/剧情/剧情梳理_v1.0.md` 的核查结果为准。

## 2. 先分清四种状态

每一段剧情都要标记状态，不能只写“已接入”或“未完成”。

| 状态 | 含义 | 允许的结论 |
| --- | --- | --- |
| 原稿明确 | 文稿直接写出人物、动作、文本、选项或结果 | 可以作为剧情要求记录 |
| 工程已实现 | 事件、地图、素材或运行时已有对应实现 | 可以列为现状，不代表与新稿完全一致 |
| 可直接接入 | 语义明确，已有运行时能力和素材，缺少数据接线 | 可以进入实现排期 |
| 待确认或缺资源 | 入口、时序、素材、名称、规则或表现方式不明确 | 先列问题，不能用猜测封闭 |

工程代码、旧策划讨论和剧情梳理文档可以证明“现在做到了什么”或“过去怎么决定过”，它们不能悄悄替换用户指定的新稿。发生差异时，报告应同时写出“原稿要求”和“工程现状”。

## 3. 剧情稿符号对照

### 3.1 角色名加冒号：对白

格式：

```text
C：“别碰线。碰了会——”
主角：“嗯？”
```

解释：这是玩家阅读的对白。每一行保留为一条有顺序的对白记录；连续两行也不要因为说话人相同就擅自合并，因为中间可能需要停顿、表情变化、镜头或输入。

当前工程通常转换为 `say` 的 `lines`：

```json
{
  "do": "say",
  "lines": [
    { "speaker": "C", "portrait": "c_base", "side": "right", "text": "别碰线。碰了会——" },
    { "speaker": "我", "portrait": "protagonist/puzzled", "side": "left", "text": "嗯？" }
  ]
}
```

说话人映射要统一：

| 原稿写法 | 当前工程常用值 | 说明 |
| --- | --- | --- |
| `主角` | `我` | 对话框中的显示名沿用当前工程约定 |
| `C`、`A`、`B`、`老人` | 原名 | 不自行改成编号或内部 ID |
| `？？？` | `？？？` | 身份未揭示时保留问号 |
| 未写说话人 | 不写 `speaker` | 当前对话框把它当作旁白，两边立绘都不亮 |
| `主角os` | 主角内心内容 | 当前数据没有独立的 `os` 字段。现有工程可用无说话人对白或标为 `我` 的对白表达，但两者呈现不同；需按既有章节样式或策划决定，不能自动等同于画外音或 `caption` |

引号中的省略号、破折号、重复字、刻意断句和不完整句子都属于文本内容。比如“可是，可”或“别碰线。碰了会——”需要原样保留，校对意见单独记录。

### 3.2 `【】`：玩家可见的非普通对白内容

本项目既有稿件约定把 `【】`作为旁白标记。转换时先按无说话人的叙述处理，再根据内容和位置要求决定最终显示位置；方括号本身不会告诉运行时应该放在对话框、左上角地点栏还是屏幕中央。

| 原稿形式 | 优先解释 | 当前工程落点 |
| --- | --- | --- |
| `【获得 半张学生证 x1】` | 获得提示或物品结果 | 节点 `set` 写入 `item/student_id`，可用 `image` 展示物品，获得提示由系统或事件补出 |
| `【贴满旧通知……】` | 玩家调查后看到的旁白 | 地图交互事件中的无说话人 `say` |
| `【傍晚】`等时间地点短注 | 场景信息旁白 | 若要求固定显示在左上角，转为 `location`，不照搬成对话框文本 |
| `【end 4 自以为是的到来】` | 结局标题或结局文字 | 若要求屏幕中央呈现则用 `caption`；节点是否写 `ending` 由实际流程决定，结局 ID 必须查 `data/endings.json` |
| `【两行文字呈现中心对称……】` | 演出排版要求 | 转成 `caption` 的行数、字体大小、等待和淡出参数 |
| `【两个秋千，一个在动……】` | 调查时的旁白或画面描述 | 先保留旁白语义；若还要求真实画面变化，再用地图物件或透明特效实现，缺少素材时列入美术缺口 |

如果 `【】` 内是画面描述，必须拆成“玩家看到的文字”和“需要美术或程序实现的视觉效果”两栏。括号内的文字也不能因为看起来像旁白就直接放进对话框。

### 3.3 `（）`：演出、交互或制作说明

括号内容默认是给制作人员看的指令，不显示给玩家。它需要再分三类：

1. **可执行演出**：例如“黑屏”“切地图”“C站在秋千旁”“点击/确认后眨眼”。对应 `fade`、`goto`、`npc`、`wait_click`、`eye_open` 等指令。
2. **地图交互**：例如“互动旗杆”“互动沙坑”“交互传送点”。对应地图 actor、portal 或事件入口；地图数据按地图编辑器流程保存。
3. **制作备注**：例如“具体效果待策划”“此处建议存档”“备注：纠缠在一起吧”。进入实现说明或待确认清单，不直接显示。

括号中有“第一段”“第二次”“后续再次互动”等时间限定时，必须转成状态或一次性触发条件。单写在备注里不能保证运行时只触发一次。

### 3.4 `{选择...}`：选项声明

格式示例：

```text
{选择① 同意组队}
{选项③ 准备好了}
{选项④ 我再逛逛}
```

它表示玩家看到的选择或作者为选择编号建立的分支锚点。实现时不要把“①”“③”直接当作运行时 ID；应建立稳定、可读的 ID，例如 `join`、`ready`、`later`，再把文稿编号记入实现对照表。

当前工程使用：

```json
"choices": [
  { "id": "ready", "label": "准备好了", "next": "go_to_school" },
  { "id": "later", "label": "我再逛逛", "next": "wait" }
]
```

选项需要同时确认四件事：显示文字、是否可选、选择后写入的状态、跳转目标。原稿只有选项文字而没有拒绝出口时，不自行补一个新的剧情分支。

### 3.5 `if①`、`if②`：分支回指

`if①` 或 `if②`通常表示“回到最近的第①或第②个选择分支”。它是稿件阅读标记，不等于当前工程的 `if_panel`。

制作时要先建立分支表：

| 文稿标记 | 对应选择 | 状态键 | 进入节点 | 合流节点 |
| --- | --- | --- | --- | --- |
| `if①` | 选择①的实际标签 | 由实现确定的稳定键 | 节点 ID | 节点 ID |

只有原稿明确出现“玩家修改 `if ... then ...` 规则”、条件块、候选块或拖拽规则时，才使用 `if_panel`。普通的“如果玩家选择了……”使用 `choices`、`set` 和 `next_when`。

`docs/IF机制.md` 是 IF 面板的唯一机制说明。不能因为剧情稿里出现英文 `if - then`，就把所有条件句制作成 IF 面板。

### 3.6 `备注`、作者说明和占位符

以下内容默认不显示给玩家：

- `备注：……`
- `具体效果待策划……`
- `道具xx`、`道具x1`等未定名称。
- “此处加一个 CG”“可插入音效”等制作提示。
- “后续再处理”“待确定”等工作状态。

这些内容要进入实现对照表的“待确认 / 素材 / 技术方案”栏。占位符不能直接被程序员替换成看起来相近的现有道具。当前项目把“道具 xx”暂时映射为 `item/charm`，这属于已记录的工程决策，不代表所有新稿中的 xx 都自动等于御守。

## 4. 段落怎样拆成可制作单元

阅读一段原稿时，按下面顺序拆分，不按换行数量机械拆分：

1. **场景入口**：当前地图、时间、镜头位置、玩家控制权。
2. **前置条件**：首次互动、已有物品、状态、是否允许重演。
3. **画面状态**：角色位置、姿势、遮挡、背景、音效、是否黑屏。
4. **玩家可见文本**：对白、旁白、提示、字幕、物品图。
5. **玩家动作**：点击、移动、交互、选择、小游戏输入。
6. **结果和状态**：获得物品、设置标记、计数变化、失败、重试、结局。
7. **控制权交接**：自动进入下一个节点、等待玩家、交回地图自由探索、切换地图。
8. **制作备注**：素材、排版、待确认问题和验收方式。

一个运行时节点通常由三部分组成：

```text
stage 演出和交互前置
→ node-level talk 或 stage 中的 say
→ choices / next / next_when / ending
```

节点的顺序是固定的：`stage` 先执行；节点级 `talk` 随后执行；对白结束后才显示 `choices`。需要在对白中间插入移动、黑屏、音效或图片时，把每段对白也写成 `stage` 中的 `say`，与动作按顺序交替；若需要交还玩家控制、等待互动或建立分支，则拆成多个节点。不要把全部对白留在节点级 `talk`、再期待动作插进对白中间。

## 5. 原稿到工程的字段映射

### 5.1 事件和节点

每个独立可进入的剧情交互使用 `data/events/<event_id>.json`。事件根部写 `id` 和 `entry`；剧情节点用稳定的 `id` 连接。

| 剧情意图 | 当前字段 | 注意事项 |
| --- | --- | --- |
| 自动演出一段内容 | `stage` | 指令按数组顺序执行 |
| 说话 | `stage` 中的 `say`，或节点级 `talk` | 连续对白可用节点级 `talk`；对白与动作交错时改用有序 `stage.say`，必要时拆节点 |
| 选择 | `choices` | 每个选项写 `id`、`label`、`next`，需要时写 `set` 或 `if` |
| 节点自动写状态 | `set` | 物品使用 `item/<id>`，剧情状态使用稳定的分组键 |
| 根据状态分流 | `next_when` | 条件和目标都必须完整，不能只写半个条件 |
| 终止并记结局 | `ending` | 查结局表，不按数字猜 ID |
| 交互后回到地图 | 节点结束且无 `next`，或挂接临时 NPC 的 `talk` | 要确认控制权是否回到玩家 |

### 5.2 常用 `stage` 指令

| 原稿写法 | 指令 | 典型用途 |
| --- | --- | --- |
| 淡出、黑屏、亮回 | `fade` | `to: black` 或 `to: clear` |
| 屏幕正中多行字 | `caption` | 心声、结局文字、需要等待玩家的字幕 |
| 黑屏章标题一行字 | `banner` | 章标题等单行大字 |
| 左上角日期地点 | `location` | 时间、地点标记 |
| 右上角提示 | `hint` | 短提示、存档建议 |
| 播放音效或音乐 | `play_sound` / `music` | 路径必须核对实际文件 |
| 等时间或等输入 | `wait` / `wait_click` | 不要把“点击/确认”默认为自动继续 |
| 放置临时角色 | `npc` | 必须保证 ID 唯一、资源和位置明确 |
| 移动、换姿势、移除角色 | `npc_move` / `npc_pose` / `npc_remove` | 角色必须先通过 `npc` 出场 |
| 玩家走位或摆位 | `place_player` | 需要核对碰撞、朝向和控制权 |
| 换地图 | `goto` | 必须同时明确地图 ID 和出生点 |
| 图片或 CG | `image` / `image_hide` | 区分屏幕中央大图、背景图和半身像 |
| IF 规则面板 | `if_panel` | 仅用于实际 IF 机制，不用于普通条件句 |
| 救援小游戏 | `rescue` | 复用现有 `RescueTiming`，不在剧情 JSON 重写判定 |

### 5.3 对白、立绘和站位

台词的内容和表现要分开记录：

- 文稿确定台词文本。
- 制作表确定说话人、头像、左右位置、表情和是否需要地图角色。
- 地图小人使用 `res://art/npc/...`；对话半身像使用 `res://art/portrait/...`。
- `C` 的地图小人、C 的半身像和 C 的束缚效果是三类不同资源，不能只因名字相近就互换。
- 新增半身像已经入库时，也要明确哪些台词切换到新表情；文件存在不代表事件已经引用。

## 6. 已完成剧情的对照案例

### 6.1 第一章开场：字幕、地点、对白、选择

原稿中的黑屏心声落为 `caption`；醒来后的日期地点落为 `location`；老人进场、移动和对白按 `npc`、`npc_move`、`say` 顺序执行；接受或拒绝委托落为 `choices`。

这个案例说明：

- “黑屏出现几行字”不是普通对白，使用 `caption`。
- “出现对话框”属于演出结果，不能把括号本身显示给玩家。
- 一个选择节点可以有多个出口，每个出口都可以写状态并指向不同节点。
- 旧稿中的 `if①/if②`需要先还原成实际选择关系，再决定是否写状态分流。

### 6.2 第二章操场调查：地图交互、获得物品、展示图片

操场地图的旗杆、沙坑和秋千是地图对象；对象的 `actions` 绑定事件 ID。沙坑事件进入后写入 `item/student_id`，展示半张学生证，再用对白解释“六年二班”。

这个案例说明：

- “互动某物”通常由地图对象提供入口，剧情事件负责内容和结果。
- “获得某物”至少要核对状态键、物品名称、提示文本和图片路径四项。
- 同一张背景里已经画出的家具不应再次切成独立贴图；确需独立效果时才添加 `art/props` 或特效层。
- 地图数据遵循地图编辑器流程保存，不直接手改 `data/maps/*.json`。

### 6.3 秋千救援：小游戏、失败、重试和合流

秋千事件先自动存档，放置唯一的 C，再显示“别碰线”。小游戏通过 `rescue` 指令写入成功标记；成功和失败通过 `next_when` 分流。失败节点提供重试和正式结束两个选项，成功节点写入 `ch2/rescued_c`，随后赠送御守并挂接 C 的后续交互。

这个案例说明：

- “第一次互动自动存档”必须成为明确的 `save`，不能只写在备注里。
- “失败可重试”需要真实回到小游戏入口，并验证束缚、计数、面板和临时角色是否恢复。
- “同一个 C”必须复用同一临时角色 ID；不能成功后再生成第二个 C 留在地图上。
- “成功后开放后续对话”通常通过临时 NPC 的 `talk` 事件交回地图控制权。
- 小游戏规则由 `core/rescue_timing.gd` 统一负责，剧情事件只负责入口、成功标记和后续分支。

## 7. 素材核查规范

策划可能在 `art/` 中追加素材，所以每次接剧情前都要重新扫描目标目录，不能只依据旧说明或上一次清单。

核查顺序：

1. 先查项目内是否已有同名或同用途素材。
2. 再查素材尺寸、透明通道、帧组、导入文件和实际显示用途。
3. 区分背景图、地图物件、角色帧、半身像、CG、UI、特效和音频。
4. 查看 README、manifest 和事件引用，确认“入库”与“已接入”不是同一状态。
5. 若美术目录存在新文件但剧情说明未提到，列入“已发现素材，待确认用途”，不要擅自替换旧图。
6. 若原稿描述了画面但没有资源，写清楚缺少的内容、建议尺寸/透明要求、出现时机和是否可用程序效果暂代。

交付前至少核对：

- 资源路径可被 Godot 加载。
- 使用的角色 ID、地图 ID、物品 ID 和结局 ID 已存在或已明确新增。
- 角色没有重复生成，离场、换图、读档和重试不会残留。
- 状态图是互斥切换还是独立叠加，按美术说明执行。
- 图片、音效、CG 和对话头像没有把“参考素材”误当成“正式调用素材”。

## 8. 待确认问题的写法

发现不明确处时，问题必须绑定原稿位置和实现影响，不能只写“这里不清楚”。推荐格式：

| 原稿位置 | 已知内容 | 不明确点 | 影响 | 需要谁决定 |
| --- | --- | --- | --- | --- |
| 选择①后 | C 要赠送一个道具 | 道具 xx 是否正式叫御守 | 物品 ID、图像、后续伏笔 | 策划 |
| 传送到教学楼 | C 说在楼梯集合 | 教学楼是否需要独立走廊/楼梯地图 | 地图、美术、出生点和 C 位置 | 策划/美术 |
| 再次互动秋千 | 有黑毛和摇动铁链 | 是否需要透明特效和铁链音效 | 美术、音频或程序临时效果 | 策划/美术 |

问题解决前可以做不依赖它的准备：整理对白、建立节点草稿、核对现有资源、准备测试清单。涉及入口、身份、物品语义、失败规则和关键时序的决定不能由程序自行补齐。

## 9. 制作流程

### A. 读稿和标注

先截取用户指定的连续段落，保留原段落顺序。为每段标注：场景、可见性、说话人、动作、交互、状态、分支、素材和问题。

### B. 建立实现对照表

每个段落至少有以下字段：

```text
原稿段落编号
原文摘要或原句
玩家是否可见
运行时类型
事件 / 节点 / 地图入口
状态键或物品键
素材路径
现有实现
缺口
待确认问题
```

### C. 先接结构，再接表现

先确认事件图能从入口走到所有结果，再接头像、音效、图片、镜头和动效。结构检查包括：

- `entry` 存在且指向有效节点。
- 所有 `next`、选项出口和 `next_when` 目标存在。
- 结局节点写入有效的 `ending`，不再继续跳转。
- 临时角色先 `npc` 后 `npc_move`、`npc_pose` 或 `npc_remove`。
- 地图事件 ID、物品键、素材路径和出生点都能解析。

### D. 验证玩家流程

按真实入口检查：

1. 首次进入和首次交互。
2. 每个选项及其状态结果。
3. 失败、重试、取消和返回地图。
4. 第二次互动、一次性触发和已完成状态。
5. 保存、读档、换地图和重新进入。
6. 结局记录、物品重复领取和角色残留。
7. 关键美术效果在遮罩、黑屏和窗口缩放下仍可见。

数据测试通过只能说明结构和部分状态正确。真正的剧情验收还需要从玩家可达入口运行到结果，并确认玩家能理解屏幕上的变化。

## 10. 常见误读

- 把所有括号都显示成对白。
- 把所有 `【】` 都当作 CG，忽略它可能只是调查旁白或获得提示。
- 看到 `if` 就新增 IF 面板，忽略普通选择和状态分支。
- 把“第一次”只写在注释里，没有 `once`、状态或条件保护。
- 把“后续再互动”做成新的重复角色或重复发放道具。
- 把地图小人、半身像和整张动作表当成同一种素材。
- 把“进入教学楼”当成已经确定了地图、出生点和集合位置。
- 把“可插入音效”当成必须已有的资源，或反过来把缺少音效当成剧情已完成。
- 把旧文档里的建议、测试录屏或素材入库记录写成新稿已经实现。
- 为了让事件通过校验，自行补上原稿没有的拒绝分支、人物动机、道具名称或结局条件。

## 11. 交付格式

每次剧情接入交付以下四部分：

1. **实现摘要**：接了哪些节点、地图入口、状态和素材。
2. **素材核对**：已使用、已发现但未使用、缺少和待美术确认的文件。
3. **不明确项**：逐项写原稿位置、影响和需要决定的人。
4. **验证证据**：数据检查、聚焦测试、真实入口、截图或录屏；明确哪些仍需用户实机确认。

不要用“全部完成”替代证据。剧情文档归档、事件结构通过、测试通过、录屏完成和玩家实际体验分别记录。
