# 同步说明 · 发包方（给对面的 AI Agent 执行）

本仓库有几百 MB 美术素材，走网络 `git push` / `git fetch` 传不完
（`git fetch` 还不支持断点续传，中断就得从零开始）。
**规则：每次同步只产出「一个包文件」交给对方，不走网络。**

---

## 任务

在仓库根目录执行，产出**一个文件**。

### 0. 先提交（硬性）

```bash
git status --short
```

必须为空。不为空就先把改动提交：

```bash
git add -A
git commit -m "<说清这次改了什么>"
```

**未提交的改动不在包里** —— 直接打包等于没发。

### 1. 生成包（二选一）

**A. 增量 bundle（推荐，包最小）** —— 对方会给一个 BASE 提交号：

```bash
git bundle create ../handoff.bundle <BASE>..HEAD
```

本次的 BASE：`70892ac9546af8aaf4136ccaa28ce5f9110f691c`
（对方每一轮会更新这个号；它必须是对方已有的提交，否则对方拉不动。）

**B. 全量 bundle（没有 BASE 时用）**

```bash
git bundle create ../handoff.bundle --all
```

### 2. 自检（必做，发之前）

```bash
git bundle verify ../handoff.bundle
```

- 退出码必须是 0；
- 输出里应有 `contains these refs:` 且列出分支；
- 出现 `error` / `does not exist` 就不要发，先排查。

顺便确认包里确实有本次的提交：

```bash
git bundle list-heads ../handoff.bundle
```

### 3. 交回

把**上级目录**里的 `handoff.bundle` 发回给对方面（单个文件）。

- 若超过 300MB：分卷压缩（`.zip` / `.7z` 分卷）或走网盘，别拆成多个 git 包。
- 不接受的替代品：`.git` 目录的**压缩包**对方也能吃，但那不是首选（体积大一倍）。

---

## 硬性要求

1. **先 commit**，再打包。
2. **打包时 git 必须空闲**：不要在 fetch / merge / rebase / 提交过程中打包。
3. **只读仓库**：这个任务不改仓库里的任何文件，产出物在仓库**外面**（`../handoff.bundle`）。
4. 不要为了「减小体积」删素材、加 `.gitignore` 或改写历史 —— 那会让对方合并出问题。

---

## 对方会怎么用（仅供参考，你不需要执行）

对方在**自己的**仓库里跑：

```bash
python tools/sync_from_package.py "<handoff.bundle 的路径>"
```

脚本会：把分支拉进 `pkg/<分支名>` → 跑 `tools/check_data.py` → 报告本次多了哪些提交、
动了哪些 `data/` 文件 → 经确认后再合并。
这个脚本在两边的 `tools/` 里都有同一份，但**发包时不需要它**。
