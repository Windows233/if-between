# 工作方法

## 先分清四个状态

每个工作项保存稳定ID、制作状态、交付状态、集成状态、验收状态、负责人、证据与下一动作。

| 实际情况 | 登记方式 | 下一任务 |
| --- | --- | --- |
| 用户说做完但未交GitHub | 制作完成（用户确认）；待提交；未核实合入；待验收 | 程序补交提交号和运行说明，接收方核验；不再实现一次 |
| 图已做好但漏打包 | 制作完成（用户确认）；待补文件；待接入；待验收 | 需要时补收，用户要求跳过就不占制作工时 |
| main有资源但无剧情引用 | 素材已交、已入库；剧情未接或待确认；显示待验收 | 排引用、显示和剧情验收；不是重新出图 |
| 本地/功能分支有、main无 | 标明分支/路径/提交；待合入；主线未验收 | 查看差异后合入与回归，不假装主线已有 |
| 旧表说要做、没有交付信息 | 待确认交付 | 开工核查；有稿返修，无稿首版；不能宣称未制作 |

用户最新报告决定“团队确认完成”的事实；工程查验决定当前仓库/运行版本状态，两者并存。只针对明确报告的范围更新，不把“小游戏做好”扩展成两次追逐、回溯或整章已完成。

## 证据与复用

以项目根定位下列入口，文件改名时搜索对应功能，不能因为路径失效就造第二套资料：

- 当前剧情正本由`docs/剧情/README.md`确认，不靠文件时间戳。
- 进度与近期变更查`docs/交接须知.md`和`docs/开发纪要.md`的进度节。
- 素材来源和选用查`art/catalogs/`、最新美术任务和实际图片；对照main与工作分支。
- 游戏进度查`data/events/`、`data/maps/`、物品/结局表和定向调用。对关键标志同时找读和写，确认入口能走到出口。
- 现有时机按键、演出导演、IF选择、背包、存读档、地图编辑器、已绑定音效优先复用。是否能复用以实际能力为准，不因名字相似就视为完成。

剧本事实保持：日记是介入媒介；回溯恢复首次进馆前物品快照；第二遍闪避是物理动作，失败为End6；逃到教学楼后在教室从窗抛御守，主角不跳窗；完整章末为End7。若新版正本改变这些事实，更新项目账和方案，不把旧事实强加给新稿。正文结局序号与稳定内部ID分别登记，不随意重命名`end4_iron`。

## 每日两小时怎么切

先确认一项当天可验收的核心成果，再安排必要输入和检查。总和包含10至20分钟共同对齐，以及交接、导出和测试。其他成员的材料未交，不可把程序两小时排满依赖它的代码。

每条至少写“在什么入口、做什么、交到哪里、怎么判通过”。例如：程序交已有救援提交，记录练习不解线、正式成功0/1/2/3状态、失败重试、御守只发一次；音效检查成功/失败/完成各响一次，重试不叠音。避免只有“完善小游戏”“优化剧情”“统一风格”等无法验收的话。

程序交付次序为：整理本地变更/提交→功能检查→仓库要求的验证→推送和提交号交接。准备分支不等于已在GitHub交付，不安排先推再测。

把分工接起来：文案交触发/正文/选择/结果/重复调查/声音提示；美术交无字底图、文字预览、透明图与位置说明；音效交文件/开始时机/是否循环/停止条件；第二美术收敛实际视觉与资源路径问题；程序交提交号、可运行版本、复现步骤和检查记录。用户只负责统筹，不给用户加制作任务。

## 冻结与缩减

剩余制作工时按“制作日数×120分钟/人”核算，不把空闲岗位的工时加给程序。关键依赖每日滚动；某项超时就用预先指定的最小表现并保留未完成状态。

最先砍新CG、额外表情/逐帧攻击、多段新地图、独立机关盘和第二套判定UI。走廊可单段，盒子用简单开启交互，追逐/闪避可复用已锁定的时机按键和演出，但规则变更必须标成方案、待用户确认。不能因为减图而丢掉日记、合照、背叛证据、追踪御守或回溯物品逻辑。

D6冻结内容，D7优先阻断和存读档，D8优先文字/视听/操作反馈，D9最终通关与打包复测。若D6主线尚未通，不宣称还有完整三天润色，也不悄悄挪日期；给出最小闭环方案及要延期/降级的项，保留用户决策。

## 计划与进度文件

`docs/项目进度.json`存项目约束、核查版本、逐项四状态、证据、下一动作、待确认输入。每日`day_plan.json`保存5名制作成员的任务分钟数；长线里程碑另列，不把可选项混进今日预算。

先用项目`tools/validate_daily_plan.py`验证，再人工核对事实。Word从当日稿生成，同一内容保持一致。计划写完不把任务置为完成；只有收到证据后再更新进度账。
