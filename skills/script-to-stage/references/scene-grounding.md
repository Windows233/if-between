# 在实际游戏场景里编排

本流程先回答“这段戏在当前游戏里能怎样呈现”，再写对白与时序。不能用纯文学剧本或假想场景替代查验。

## 必须取得的工程证据

1. **场景文件与画面**：定位地图/场景ID，读尺寸、背景、入口、actor、rect、reach、portal、walls、cover。打开实际背景与相关遮挡图。记录查过哪些图片；文件存在不等于画面已看过。
2. **玩家实际视野**：从工程核实逻辑视口、地图缩放、相机边界及对话框占屏区域。大地图底图不代表玩家同时能看全图。“全景”“拉近”要说明是否符合当前相机能力；无缩放指令不能当现有能力。
3. **演员与物件**：检查人物是否已经画在底图，独立人物是否有方向帧/蹲下/攻击等真实动作，立绘和地图小人分开。地图角色ID、临时角色ID和对话称谓分别绑定，避免重名或双份人物。
4. **空间关系**：位置均用游戏逻辑坐标，锚点是脚底或头部要明确。交互点rect不等于可站位置，reach不等于可走区域。只从背景看起来空旷不能证明可走。
5. **播放能力**：查相关原生事件与执行函数，判断镜头、人物、图层、音频、遮罩、交互是否已有对应。不要只背一张指令表；核实此次用到的参数。

可使用当前Godot编辑器和运行窗口的只读检查/截图。若需要操作正在运行的Godot，使用可用的gdmcp技能；没有运行环境时读文件和实际图片也可以，但记录 `runtime: not_run`，不能声称实机验证。

## 空间编排

- 探索调查默认保留玩家走到物件时的位置，不为“构图好看”突然瞬移。若必须排站位，说明接管控制时刻、从哪里走到哪里、碰撞是否允许、镜头何时恢复。
- 走路路径用现有WalkGrid与路径探针或等效真实碰撞验证。`tests/probe_route.gd`可检查地图静态路径；还要考虑新增NPC碰撞。工具若返回的是目标附近可站点，使用实际返回终点，不能把原始目标说成已验证。
- 未运行路径检查就写 `route_status: unverified`。可先采用原地对话完成不依赖走位的段落；原文要求移动且必须验证时，保留draft和明确待验路线。
- 不凭像素原图直接抄逻辑坐标：读取map size和贴图实际尺寸，核实缩放。现有JSON actor坐标可作为绑定依据，人物脚底仍要核实。
- 摄像机与对话框左右槽位不能代替地图走位。镜头看向秋千，不代表主角已经站在秋千前；side:right只管立绘槽，不管C的地图位置。

## 演出取舍

优先级：已有地图小人/方向帧与遮挡 → 已有立绘/道具图 → 简单现有镜头与淡变 → 明确列出的新素材或机制。不是每句台词都要移动或换镜头；有内容意义才安排。

原文写“伸手救人”，当前只有站姿时，可以写“主角原地朝向C，因果线的变化表达介入；伸手专用帧缺失”。若伸手不是剧情必要动作，站姿为低影响呈现方案；若必须准确表现动作则列新素材，不偷偷改剧情。

原文写“C被线缠住”，底图却是C站在秋千旁，必须先说明替换/局部修图或分层需求。不能一边保留底图C，一边再生成一个会走的C，还把它当已实现。

## 给实现AI的交接

每段需指明：

- 地图和源文件，例如 `school_yard → data/maps/school_yard.json`。
- 触发位置，例如 `actors[id=swing].actions[id=check].event → ch2_swing`，是否保留once。
- 实际已有表现与要改的差异，不能把旧事件里已有两句对白当整段救援完成。
- 逐步指令/状态拆分，引用原生 do 与参数；缺能力写 `requires_work` 或 `unresolved`，不编造指令。
- 最终站位、人物去留、镜头、背景、音乐与玩家控制权；下一段可直接继承这些已知结果。

输出中的“已具备”必须有文件证据；“已验证可走”必须有对应工具结果；“画面已验证”必须有实际截图。单凭推断均用准确的较低验证级别。

## Markdown说明结构

每张地图按以下顺序写，内容取自同源YAML：

1. 这段发生在哪里：真实场景ID/背景/视口/物件布局，简述哪些是底图、哪些是独立节点。
2. 触发与起始站位：实际交互点，玩家控制方式，角色朝向、镜头与遮挡。
3. 演出表：步骤ID｜玩家看到/听到/做什么｜用到的实际对象与原生指令｜何时继续。
4. 接入与结束状态：哪个事件承接、哪些flag/物品何时变化、控制权归还、后续入口。
5. 当前缺口：具体阻塞、可完成片段、需要补的资源/机制和验收方式。

不需要编造长篇场景形容词。画面说明应能让实现者在现有工程里定位并操作对应对象。
