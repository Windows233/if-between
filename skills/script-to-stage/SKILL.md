# 剧本演出编排

把用户剧本编排成**在当前游戏的真实场景里如何发生**的制作文件。默认交付 UTF-8 的 `<事件>.stage.yaml` 及由它派生的 `<事件>.stage.md`：前者供实现AI精确读取，后者供用户审阅场景和演出。它们描述同一份内容，不分别创作。文件必须绑定真实地图、已有物件、角色素材和当前演出代码，不能只是文学剧本外加“镜头拉近”等泛化说明。

本项目是320×180逻辑视口的二维像素游戏，实际参数每次从工程核实。优先复用地图、调查物、角色朝向帧、立绘、道具图及现有演出指令；不要按电影或3D游戏假设移动镜头、特写、动作捕捉。YAML不是引擎直接加载的事件JSON，但已有能力对应的每步必须给出实际原生指令或明确的数据拆分位置。

## 使用顺序

1. 读取用户指定剧本及直接相关资料，定位原文来源。读 [格式规范](references/format.md) 和 [实际场景编排流程](references/scene-grounding.md)。首次使用可参考 [易拉罐结构示例](references/example.stage.yaml) 和 [操场救C场景说明示例](references/swing-grounded.stage.md)。
2. **先查工程，再写演出。** 本项目读 [项目接入说明](references/if-between.md)，定位对应地图JSON、事件、背景、分层与角色。读取JSON还不够：必须查看将要使用的真实背景/关键角色图片，检查哪些人物与物件已经烘焙在底图。用户给的是别的工程，则按那个工程重新核实，不能只套通用剧本格式。
3. 记录 `game_context`：实际地图尺寸/视口、入口、物件rect/reach、墙体与遮挡、可用角色动作、镜头约束、画面查验来源。提炼剧情事实与状态链，将每个场景绑定实际地图；无现成场景时明确列新场景需求，不能凭空声称已存在。
4. 在真实位置上安排触发、走位、朝向、画面焦点、对白和玩家操作。每条cue附 `engine` 实现对应。按场景/交互/分支/状态时刻拆节点；未知坐标或不可走路线不能伪装成可直接实施。每条动作、台词、声音、状态有独立cue。
5. 检查完整行动链和演出收尾，运行结构与场景绑定检查。Markdown按“实际场景→站位和触发→逐步演出→游戏接入→缺口与验收”生成，不写成脱离地图的纯对白稿。用户只要求演出文件时不自动修改游戏或素材。

## 忠于剧本，但补足实现所需信息

- 用户本次指定版本及明确修订优先。同名文件或较新时间戳不自动代表已批准；“待采用”“建议”“未定”不能升级成既定剧情。
- 原台词逐句保留，用 `mode: spoken / thought / narration` 区分说出口、心声和旁白。策划备注、镜头说明和制作限制不可混进玩家对白。用户要求润色时，记录改动范围。
- `origin: source` 表示原文事实；`staging` 表示为呈现原文补充的低影响安排；`proposal` 表示会改变事实、规则或玩法的待定建议。每条 cue 都关联 sources。
- 可自主安排合理的停顿、淡入、朝向、先后顺序和文字摆放；不要自行增加人物动机、凶手身份、关键道具用途、结局、惩罚或回溯规则。
- 缺镜头参数通常可以给出具体演出方案并标为 staging；缺决定剧情走向的信息，登记 decisions，标明受影响节点和 `blocking: true`。继续完成不依赖它的部分，不凭猜测填成事实。
- 缺图、缺动画、引擎尚不支持的操作要记录资源/能力状态及可行替代。替代不改变原剧情时可直接编排；涉及改变玩法或剧情时标为 proposal。不要把概念图或存在于底图的人物当成独立可动素材。

## 把画面写到可以执行

不要只写“气氛诡异”“紧张起来”“C救下主角”。也不要写“C从右侧门口走来”却没有检查这张图右侧是否有门。本游戏每条说明须落到真实对象，例如：“在school_yard复用swing交互点；锁定玩家控制，镜头保持地图比例，展示秋千旁的C；先处理底图已画入的C，才允许叠独立角色。”坐标、动作与路线必须来自实际查验。

每个节点说明：在哪里、何时触发、哪些人物可见、人物位置和朝向、镜头看哪里、环境与背景音乐、玩家当前能否移动。沿用前态必须明确写 `inherit`，不能让实现者猜。

每条 cue 说明：

- **做什么**：一个可观察动作；台词写精确文字、说话人、模式、对话框左右槽位与立绘资源。
- **何时开始与结束**：默认上一条结束后执行；等待用 finished / confirm / interaction_result，自动继续才写 seconds。不要用固定一秒等待冒充玩家读完长段文字。
- **作用于谁**：稳定 entity ID；地图位置用已核实坐标或锚点。`screen_left` 是屏幕构图，`map` 是地图坐标，对话框 `side` 不是角色地图位置。
- **什么时候改状态**：拾取物实际展示时、选择提交时、小游戏成功时等，用有顺序的 state cue 表示；不要把奖励提前放在节点入口。
- **什么时候撤掉**：持续图片、临时人物、提示、循环音效、镜头偏移、遮罩都需要明确恢复或显式交接给下一节点。

时长是演出建议而非实测；不知道地图尺寸时不要凭空给像素坐标。可用 `anchor` 描述“易拉罐交互点前的可走位置”，在对应参数中写 `binding: null`，并登记 decisions。必须核实的绑定未完成时保留 draft。

## 交互和分支

- 普通阅读、选择、自由探索、小游戏、不可操作剧情分别表达。强制剧情失败不能伪装成可赢挑战。
- 选项逐项写标签、可见/可选条件和出口；错选反馈、取消或未操作的处理、重试入口要可追踪。
- 新小游戏描述输入、目标、成功判定、错误计数、反馈、暂停、失败与重试恢复，不只写“这里加入小游戏”。这些是需求，不能宣称引擎已实现。
- 有意循环写明退出条件和保留状态；重复调查、奖励只发一次、物品获得/消耗、回溯与存读档分别核对。
- 原文无相关机制时不新增小游戏；不因输出格式支持分支而强行添加选项。

## 校验与交付

本项目运行 `python <技能目录>/scripts/validate_stage.py <输出.stage.yaml> --project-root <工程根目录>`。依赖PyYAML；使用可用环境，不擅自联网装包。v2会检查场景绑定和原生指令名；它不验证真实画面效果、碰撞通行或通关。

人工核对：每条原台词与关键剧情有 coverage；分支出口可到达；动作主体在场；并行动作不争用同一对象同一属性；读字期间没有未经剧本要求的惩罚计时；道具和回溯状态一致；所有持续表现有收尾；未解决事项未藏进“完成”状态。

最终 `status` 取 `draft` 或 `ready_for_implementation`。后者表示演出需求和必要绑定明确，仍不等于已经实现。缺少关键事实、无可行替代的必要资源或能力时用 draft，并说明可继续实现的节点。新增资源但已有明确可实施的制作规格，可以 ready，同时保留资源为 planned。

默认生成结合工程的演出说明与同源结构稿。说明里必须写清挂接哪个地图对象/事件、复用哪些文件、哪些原生节点需要拆分、哪些素材或机制仍缺。用户另要求直接接入游戏时，才修改原生剧情JSON和游戏代码。没有查看真实场景或必要空间绑定未核实时，禁止标ready。
